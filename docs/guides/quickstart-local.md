# Quickstart (local)

Run the whole system on a laptop with only Docker: Postgres, Redis, the AWS emulator
(provisioned by the same Terraform as production), a mock LLM provider with four endpoints,
the API and gateway, a worker and the dashboard. No AWS account and no provider keys are
needed.

## Prerequisites

- Docker with Compose v2 (Docker Desktop or Docker Engine)
- `make`, `bash`, `openssl`
- For running tests outside containers: Python 3.12 with [uv](https://docs.astral.sh/uv/),
  Node 22 and pnpm 9

## Start

```bash
git clone https://github.com/euron-sde-team/euron-open-smart-router.git
cd euron-open-smart-router
make env     # writes deploy/compose/.env with random local-only secrets and a demo password
make up      # builds images, applies Terraform against Floci, migrates, starts everything
make demo    # demo organisation, a benchmark run, 60 days of history, live traffic
```

`make up` runs `make env` for you if `deploy/compose/.env` is missing, so the first line is
optional; it never overwrites an existing file (delete it to regenerate). `make up` prints
the URLs. `make demo` prints the dashboard login, a gateway key for the Alpha Tutor project
and a ready-to-paste curl command.

| Service | URL |
| --- | --- |
| Dashboard | http://localhost:4210 |
| Gateway (OpenAI-compatible) | http://localhost:4230/v1 |
| API docs (Swagger) | http://localhost:4230/docs |
| Mock LLM provider | http://localhost:4250 (call counts at `/stats`) |
| Floci (AWS emulator) | http://localhost:4266 |
| Postgres | `localhost:4242` (user, password and database `smartrouter`) |
| Redis | `localhost:4279` |

Ports are overridable in `deploy/compose/.env` (`SR_WEB_PORT`, `SR_API_PORT`,
`SR_MOCK_LLM_PORT`, `SR_PG_PORT`, `SR_REDIS_PORT`, `SR_FLOCI_PORT`). The dashboard also
proxies `/v1/*` to the API, so `http://localhost:4210/v1` reaches the same gateway.

The first `make up` takes a few minutes: images build, and the Terraform one-shot creates
the exports bucket, KMS key and secrets inside Floci. Later starts reuse the state volume.

### What `make demo` creates

- Users: the owner `admin@smartrouter.local`, an admin and a viewer, all with the demo
  password. The password is `DEMO_PASSWORD` in `deploy/compose/.env` (generated by `make env`);
  when `seed-demo` runs outside Compose with no `DEMO_PASSWORD` set, it is `RouterDemo2026`.
- Four endpoints on the mock provider: OpenAI (mock), Anthropic (mock), Local inference
  (mock) and TokenShield gateway (mock).
- Five models: `gpt-fast` (fast), `gpt-mini` (low cost, reached through TokenShield),
  `gpt-pro` and `claude-pro` (advanced), `llama-local` (local, free per token, no tools).
- Six policies: `balanced` (the default), `cost`, `latency`, `quality`, `support-bot` and
  `code-review`.
- Four teams and five projects (Alpha Tutor, Support Copilot, Code Review Agent,
  Doc Insights, Marketing Studio), each with a production key; two also have a staging key.
- A full benchmark run, so the quality table is measured rather than guessed.
- 60 days of decision history (including a `gpt-pro` outage that opened its circuit) and
  about 130 live requests through the real gateway: routed, streamed, pinned, failed over
  and refused by a TokenShield budget.

Running `make demo` again prints `demo data already present; skipping (make down to reset)`.

## Sign in

Open http://localhost:4210 and sign in as `admin@smartrouter.local` with the password
`make demo` printed. To read it again:

```bash
grep DEMO_PASSWORD deploy/compose/.env
```

To use your own account instead (for example on a stack without the demo data), create an
owner and set its password at the prompt:

```bash
make admin EMAIL=you@example.com
```

## Your first request

With the `tsr_...` key `make demo` printed:

```bash
curl -i http://localhost:4230/v1/chat/completions \
  -H "authorization: Bearer tsr_..." \
  -H "content-type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"Solve 3x + 7 = 22"}]}'
```

`"model": "auto"` asks SmartRouter to choose. The body is a normal chat completion whose
`model` field names the model that answered. The headers explain the choice:

| Header | What it tells you |
| --- | --- |
| `x-smartrouter-request-id` | The id to search for in the dashboard (`req_...`) |
| `x-smartrouter-model` | The model that answered |
| `x-smartrouter-policy`, `x-smartrouter-strategy` | Which policy decided, and its strategy |
| `x-smartrouter-task`, `x-smartrouter-complexity` | What the analyzer saw: here `math`, complexity 3 |
| `x-smartrouter-reason` | One line on why this model won |
| `x-smartrouter-attempts`, `x-smartrouter-fallbacks` | How many models were tried, and which failed first |
| `x-smartrouter-estimated-cost-usd` | The estimate the ranking used |
| `x-smartrouter-cost-usd`, `x-smartrouter-baseline-cost-usd` | What it cost, and what the baseline model would have cost for the same tokens |
| `x-smartrouter-baseline-model` | The model savings are measured against |

The full list is in [integrate.md](integrate.md#response-headers).

The same with the OpenAI Python SDK, unmodified. `with_raw_response` gives you the headers:

```python
from openai import OpenAI

client = OpenAI(base_url="http://localhost:4230/v1", api_key="tsr_...")
raw = client.chat.completions.with_raw_response.create(
    model="auto",
    messages=[{"role": "user", "content": "Solve 3x + 7 = 22"}],
)
reply = raw.parse()
print(reply.model, reply.choices[0].message.content)
print(raw.headers["x-smartrouter-reason"])
print(raw.headers["x-smartrouter-request-id"])
```

## Find the decision in the dashboard

Open **Decisions**, paste the `req_...` id into the search box and open the row. The drawer
shows what the request looked like (task, complexity and the signals behind them), why this
model was chosen (every candidate with its score, or the reason it was filtered), the cost
against the baseline, and any fallback chain. Decisions reach the log through the worker
within a second or two.

## Watch the router work

- **Pick a policy:** send `"model": "auto:cost"` or `"auto:quality"` with the same prompt and
  compare `x-smartrouter-model` and the cost headers. Or keep `"auto"` and add the header
  `x-smartrouter-policy: latency`.
- **Pin a model:** send `"model": "gpt-fast"`. It is passed through unrouted
  (`x-smartrouter-policy: passthrough`), with no fallback.
- **Override the analysis:** add `x-smartrouter-task: coding` or
  `x-smartrouter-complexity: 5` and watch the choice change.
- **Simulate without spending:** open **Simulator**, pick an example such as "Hard coding
  task" and run it. You see the ranking the gateway would use, and no model is called.
- **Compare policies:** open **Benchmarks** for the run `make demo` did: quality and cost for
  every model and policy against the `claude-pro` baseline.
